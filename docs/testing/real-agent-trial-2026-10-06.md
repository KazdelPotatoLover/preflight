# 真实双 Agent 协作试验：Findings 工作台

试验日期：2026-10-06（Asia/Shanghai）。基线提交：`087d454`。

本文前半保留初版人工裁决前置的试验记录；后面的自主协商阶段记录用户修正方向后的实现与复测。两阶段结果不能混算。

## 目的与范围

两个独立模型 Agent 在独立 worktree 中，分别承担后端和前端的真实开发任务：在工作台展示 Findings。双方使用不同成员令牌连接同一个本地 Preflight 服务和 PostgreSQL，不预编排业务工具调用序列。

当前执行环境不能动态向 Agent 挂载新的 MCP 工具，因此使用官方 MCP SDK 命令桥接。Agent 自主决定调用哪个工具、输入什么内容，再由桥接实际调用 Streamable HTTP；这验证协作行为和协议链路，不代表已验证某个 IDE/CLI 的原生 MCP 安装体验。

| 参与者 | 工作 |
| --- | --- |
| Alice / 后端 Agent | 仓库隔离的 Findings 读取、来源关联、后端验证 |
| Bob / 前端 Agent | Findings 工作台、筛选、安全渲染、浏览器验证 |
| 用户 | 默认展示方式的实际产品裁决 |
| 协调 Agent | 环境准备、日志观察、整合、独立验收 |

初始工作约定统一要求查询项目、登记工作、读取上下文、发布发现、更新进展、重大取舍交给人、完成前提交实际证据。为控制试验，安排了一次真实接口/产品取舍，并要求先发布后端初始调查，再启动前端。此设计不能证明自然场景中 Agent 会自行识别所有重大决策。

## 初版观察

- 后端自主查询项目、登记 Change、读取上下文、发布初始 Findings、更新 implementing；不是固定业务调用脚本。
- 前端随后查询项目并登记自己的独立 Change。
- **失败：前端第一次读取上下文，相关工作和 Findings 均为 0。** 两项工作有相同 Goal，但标题/声明路径不足以触发原有相似规则；同目标不构成关联证据。
- 前端自主调查了后端服务文件，补充声明范围并反馈 `related_but_distinct`，再次读取获得后端 Findings。此方式依赖声明文件与读取目的的混合，不能视为低成本的自动发现；应由产品直接支持同 Goal 关联。
- 前端提出关联两个 Change 的阻塞决策：“工作台 Findings 默认按 Change 查看，还是全仓库时间线混排？”
- 前端后续读取确认 blocking，并等待人类裁决。

协调 Agent 将上下文缺口交给后端修复。这是一次明确的范围协调干预；修复后的成功不能倒算成初版发现复用成功。未通过私下消息把后端调查全文复制给前端。修复提交 `93467d7` 已进入整合分支并更新实际服务；后端再次读取真实 MCP 上下文，看到 `same_goal` 证据和前端的 Findings，双向共享已有日志证明。前端还主动移除了仅用于共同调查的后端文件声明，再次读取时仅凭 `same_goal` 获得相关工作与 Findings，验证修复确实生效。

## 发现的后续问题

1. 不能要求用户或 Agent 通过调整标题/声明路径来获得同目标上下文；本轮已补 `same_goal`，仍需更广的任务集验证误关联率。
2. 手机没有横向溢出，但全部 Findings 全文排列可产生很长页面，将决策区推到下方。后续应试用摘要折叠、分页或调整移动端决策入口。
3. 当前有显式的工作约定、安排好的决策场景和协调者，无法据此证明自然场景完全自动维护看板。
4. 人类决策反馈、原生客户端接入和正式交付验收仍是待验证环节。数据库/浏览器 fixture 中的裁决通过，不替代本轮用户的实际裁决。

## 自主协商阶段：取消人工前置

用户指出普通协作不能以人类选择为前提，并授权修改。旧待定事项通过版本迁移从 `pending` 转为 `negotiating`，保留原提案和选项；已有 `human_resolved` 历史记录没有改写成 Agent 共识。原 Goal 的人工验收条件按用户的新要求更新，保存 `goal.updated` 审计事件 `809f3c25-f195-4e73-8d2e-5d1a1f3d9482`，保留修改前后条件及原因；没有伪造旧条件已通过。

协议增加 `preflight_review_decision`。每项受影响工作由其参与 Agent 提交选择、理由和目标/约束/验证证据，全体接受同一选项才自动记录一致。每轮答复不能覆盖，新增影响工作会开启新周期，旧范围的意见不能充当新范围共识。三轮仍分歧进入 `deferred`，提出隔离建议；完成前须提交逐项隔离证据，不能把建议表示为已经实施隔离。仅目标边界或必要信息缺口进入 `needs_input`，普通协商失败不会自动转为人工待办。

两个原 Agent 保留独立成员、Change 和 Session，使用官方 SDK 经实际 HTTP 调用新工具；新的桥接日志位于本地忽略目录 `.preflight/autonomy/`。协调 Agent 负责协议整合和验证，没有提交代理审议、使用 human 凭据选方案，或预先指定共识选项。

实际结果：Bob 先读取修订 Goal 和 Alice 的接口/验证 Findings，选择“默认全仓库时间线”。他明确说明改变原提案建议的原因：来源与两种范围读取已实现，进入工作台默认任挑一项 Change 会遮蔽团队发现；仍保留按 Change 查询与手动选择。Alice 随后读取真实上下文与 Bob 的意见，也接受该选项，记录自己的目标、约束和验证依据。

原 Decision `c4175f78-ee1d-40c8-a885-82995e5fdd0e` 在第一个周期第一轮自动成为 `agent_resolved`，version=3，选项 `348d1c53-dec8-4676-9627-f7d57bda12a7`，两项工作均答复，缺少答复数为 0。Alice 的完成前读取显示 `blocking=false`、`recommended_action=continue`，并发布实际读取结果 Findings `2492e304`；Bob 也重新读取同一共识，然后落实默认行为。自主协商阶段人工选项确认次数为 **0**。

新增验证使用真实 PostgreSQL 和官方 SDK：从旧 001 schema 升级两次、保留历史人工结果、两 Agent 共识、审议身份/幂等/过期版本、影响范围变化失效、三轮分歧、准确隔离证据、目标信息例外、其他阻塞保留、终态不继续等待和持久化。三轮分歧及信息缺口是自动化 fixture 的验证，不能算作两个真实模型自然产生分歧后的行为。

工作台移除了普通裁决表单，展示只读协商状态、答复成员、选项、证据、轮次和历史；较长 Findings 可折叠，移动端协商区提前。浏览器测试验证共识、隔离建议、目标信息缺口、文本转义、范围切换、空态、刷新保留选择及手机布局。服务仍不运行模型或后台唤醒 Agent；真实推进依赖外部 Agent 持续调用工具，不能把这次有协调者的开发试验表述为全程无人调度。
